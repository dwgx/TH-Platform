### 1.2 键盘输入进游戏 — SendInput（今晚刚打通的方法）

**这是把游戏开进关卡的唯一可行合成输入路径。**

**原理链**（每一条都有实测或源码依据）：

1. th08 用 **DirectInput** 读键盘，**不读窗口消息** → `PostMessage(WM_KEYDOWN)` 永远进不去（旧车道实测 `cur=0x0000` 恒定）。
2. `SendInput` + `KEYEVENTF_SCANCODE` 驱动真实输入栈 → DirectInput 能读到。
3. SendInput 送进**前台窗口** → 需要焦点。owner 已授权 mouse/keyboard 使用。

**代码**：`%TEMP%\thp\input_helper\THPInput.cs` → 编译成 `thp_input.exe`。

**踩过的坑（都会再遇到）**：
- `Add-Type` 在 PowerShell 里编译完整 `INPUT` union 会 `OutOfMemoryException` → **改用独立 EXE**。
- Reference assembly 路径有空格（`Program Files (x86)`）→ **每个 `/r:` 单独加引号**。
- csc 用 **`/noconfig`**，别读它的 `csc.rsp`。
- **`INPUT` 结构体必须正好是平台大小**：x64 = 40 字节（`type` 4 + 对齐 4 + union 32）。手搓 padding 会变成 56 → `SendInput` 报 **err=87 参数不正确**。用 `[StructLayout(LayoutKind.Explicit)]` 的 union，`MOUSEINPUT` 天然 32。
- 进程完整性：medium 级别、非管理员 SendInput 可用（err=87 是结构体问题，不是权限）。

**用法**：
```
thp_input.exe focus              # 把 th08 窗口拉到前台
thp_input.exe tap 2C 3 300       # scancode 0x2C (Z) 按3次，每次间隔300ms
thp_input.exe seq "2C:80:350 50:80:300"   # 序列
thp_input.exe click              # 点客户区中心（兼带焦点）
```

**Scancode（PS/2 set 1）**：

| 键 | code | 键 | code |
|---|---|---|---|
| Z | 0x2C | 上 | 0x48 |
| X | 0x2D | 下 | 0x50 |
| Enter | 0x1C | 左 | 0x4B |
| Shift | 0x2A | 右 | 0x4D |
| | | ESC | 0x01 |

**ZUN 输入位**（DLL 读的是这个，不是 scancode）：

```
0x0001 SHOOT(Z)  0x0002 BOMB(X)  0x0004 FOCUS  0x0008 MENU/SKIP
0x0010 UP  0x0020 DOWN  0x0040 LEFT  0x0080 RIGHT
```

来源 `game/src/Global.hpp:90-106`。**之前有 brief 把这些位错移了两位**（Up 会变 shot-slow），已经被纠正。

### 1.6 SendInput 实测结论（2026-10-02 打通，附失败路径）

**结论：能进。** 但有三个必须知道的陷阱，都在实测里踩过：

**陷阱 1 — hold 必须够长（≥200ms）。**
`SendInput` 发 down/up 后再 sleep 是**错的**。`th08` 用 DirectInput **轮询**设备状态，不是接收边沿通知，按下和抬起之间没有真实时长的话，游戏下一次轮询时按键已经弹起，等于完全没发生过。
实测：hold 80ms → `cur=0x0000`（收不到）；hold 200ms → `cur=0x0001`（收到）。
代码在 `tools/th-debug/input_helper/THPInput.cs` 的 `Tap()`，注释里写明了原因。

**陷阱 2 — 采样点会骗你。**
按键后立刻读日志，很可能落在按键间隙，读到 `0x0000`，看起来像「没进去」。要看 `scene:` 行里的 `edge_frames` / `held_frames`，那是锁存后的累计值。

**陷阱 3 — 「没报错」不等于「成功」。**
截图脚本曾经丢弃截图工具的输出、无条件打印文件名，捕获失败也报告成功。已修为检查文件是否真的落盘（`Grab()` 返回 `CAPTURE-FAILED(...)`）。

**已实测跑通的完整路径**：

```
启动(窗口化) → focus → Z(开菜单) → Z(Start) → Z(确认难度) → Z(确认) → 关卡
```

**进入真关卡的证据**（不是自动播放）：

```
player2_hook: stage started by a human (g_CurFrameInput=0x0001, curState=2) - constructing g_Player2
player2_hook: g_Player2 fully wired (ctor + chain)
scene: frame=1020 curState=2 input=0x0000 last=0x0000 human=1 (HUMAN) edge_frames=5 held_frames=13
```

`human=1` + `edge_frames=5`（5 个按键边沿）+ `held_frames=13`（13 帧保持）= 真人输入被确认捕获，`0x0001` 是确凿的 Z 键。**这补上了 Phase B——之前判定「自动化测不了、必须真人」的那个缺口。**

**新增工具**：`tools/th-debug/thp_shot.exe`（`THPShot.cs`）无抢焦点截取游戏窗口，`drive_visual.ps1` 每按一键截一张图。**用眼睛判断菜单到哪了，不要靠日志猜。**

### 1.8 握手三连坑（全部实测定位，非推测）

**每一个都是「静默失败」——不加日志就永远查不出来。**

**坑 1：传了缓冲区容量而非实际长度**
`lockstep.cpp:331` 把 `datagram->bytes.size()`（容量 **512**）当成包长度传给分发函数，而不是
`datagram->size`（实际 **76**）。主机拿 512 字节去解析一个 76 字节的 HELLO，尾部陈旧数据让解码失败。
症状：`HELLO rejected MALFORMED (512 bytes)`。

**坑 2：解码了头部却扔掉**
`reader_for()` 确实调了 `thp_header_decode`，但解到**局部变量** `thp_header h{}` 就丢了。
于是 `hello.header.ver_major` 恒为 0。
症状：`HELLO rejected VERSION_MISMATCH (peer v0.0, ours v1.0)`——**发送方明明写的 1.0**。
修法：`reader_for()` 增加出参把头部交回调用方；三处回调（hello/negotiate/welcome）全部改接。

**坑 3：静默拒绝**
`on_hello` 有 5 条拒绝路径，**全部不打日志**。主机拒绝了 HELLO 却没人知道，看起来和「握手没到达」一模一样。
修法：每条拒绝路径都记明原因 + 参数；收包入口的尺寸闸门也记 `dropped datagram`。

**为什么值得记**：这三个 bug 都在 `AdaptTh08` 车道交付后存在，该车道的 **264 项单元测试全绿**——
因为测试直接调 session API，不经过 socket 收发。**单元测试覆盖不到接缝。**

### 1.9 当前精确状态

```
thp: HELLO accepted, session=0x08cb962d delay=3 caps=0x000700db blob=0B
```

握手第一步通了。**但会话仍未 connected，hash 比对仍是 0 次，同步仍未证明。**
guest 侧仍在收 HELLO 并按 guest 身份忽略，主机没有推进到 NEGOTIATE/WELCOME 完成。

**下一步**：主机接受 HELLO 后应回 NEGOTIATE+WELCOME（`on_hello` 末尾 `res.out_size = neg_n + welcome_n`，
`res.action = Action::Send`）。查 pump 的发送分支（`lockstep.cpp:333` `if (reply > 0)`）是否真的把这包发出去，
以及 guest 的 `on_negotiate` 是否被调用。**继续用日志说话，不要读代码猜。**

### 1.10 握手完成（实测），四连坑

**当前实测状态：握手走通，两边一致。**

```
host:  thp: HELLO accepted,  session=0x000044c8 delay=3 caps=0x000700db blob=0B
guest: thp: WELCOME accepted, session=0x000044c8 seed=0x0176cde7 delay=3
```

`session` 两边相同、`seed` 相同、`delay` 相同。

**坑 4：两个包塞进一个 datagram**
`on_hello` 末尾 `res.out_size = neg_n + welcome_n`，把 NEGOTIATE 和 WELCOME **拼在一个缓冲区**里发出去。
但接收路径 `handle_datagram_locked` **每个 datagram 只解一个包**（`type = data[6]`）。
guest 解完 NEGOTIATE（`on_negotiate` 按设计**静默不回包**），后面的 WELCOME 被**静默丢弃** → 握手永远走不完。

症状（加日志前完全看不见）：guest 收到 `type=1` 和 `type=2`，**永远收不到 `type=3`**。
修法：`Session` 增加 `second_offset_`，pump 按偏移**拆成两个 datagram** 发出。

**加诊断日志的顺序本身就是方法**：
1. 先给所有静默拒绝路径加日志 → 看到 `MALFORMED (512 bytes)`
2. 再加发送侧日志 → 看到「发 76 收 512」，锁定坑 1
3. 再加每包 type 日志 → 看到只有 type 1/2 没有 type 3，锁定坑 4

每一步都是**先让失败可见，再定位**。没有一步是读代码猜的。

### 1.12 失步检测首次跑通（2026-10-02，实测）

**这是本项目历史上第一次真正抓到失步。**

```
guest: thp: WELCOME accepted, session=0x587a7f8e seed=0x017a0106 delay=3
guest: thp: START proposed at frame 1
双方: INPUT 包交换 6440 / 6549 个
host: thp: DESYNC at frame 30 (remote 0x3E360DD2)
host: thp: DESYNC detected at session frame 30
host: thp: DESYNC at frame 60 (remote 0xA2A0B67C)
```

**全链路第一次贯通**：会话建立 → START 提交 → 每帧输入交换 → 60 个区域的状态哈希计算 → 比对 → **分歧被抓到并定位到具体帧号**。

**坑 5：guest 从不回发 START**
`on_welcome` 设了 `res.action = Action::Connected` 却**既没调 `build_start` 也没设 `out_ready`**——
什么都不回发。而 host 只有收到 guest 的 START 回显才会 `mark_connected_locked()`。
于是 host 永远不 Connected → `send_start_game` 被门控挡住 → 谁都发不出 START。
症状：`type=4`(START) 在日志里**一次都没出现过**，而握手看起来两边都正常。

修法：`on_welcome` 末尾 `build_start(..., THP_FLAG_ACK)` 并设 `out_size`/`out_ready`。

### 1.13 现在的诚实结论

**失步检测：已证明可用。** 它抓到的是真实分歧，帧号明确。

**同步：仍未达成。** 两个游戏在 **frame 30 就分道扬镳**。这不再是「不知道有没有同步」，
而是「知道不同步，而且知道从哪一帧开始不同」——这是能推进的状态。

**下一步**：frame 30 之前两台必然有状态差异。优先查 RNG 同步（host `seed=0x017a0106`，
TH08 只吃低 16 位 → guest 必须装同一个 16 位）和输入 delay=3 是否两边一致。

### 1.14 为什么必然分岔——架构性根因（已证实）

**`peek_remote_input()` 被声明、被定义，但没有任何调用者。**

```
$ grep -rn "peek_remote_input" dll/src/
dll/src/net/lockstep.cpp:718:std::uint16_t peek_remote_input(std::uint64_t frame)
dll/src/net/lockstep.h:41:std::uint16_t peek_remote_input(std::uint64_t frame);
dll/src/net/lockstep.h:93:// / peek_remote_input above. Phase 6g will rewire rollback to those.

$ grep -rn "remote_input|peer_input|apply_remote" dll/src/hooks/ dll/src/state/
（无输出）
```

**当前真实架构**：

|环节 | 状态 |
|---|---|
| 输入通过网络交换 | ✅ 工作 |
| 状态哈希计算 | ✅ 工作 |
| 哈希比对 / 失步检测 | ✅ 工作（抓到 frame 30 真分歧）|
| **对端输入应用到本地游戏** | ❌ **完全不存在** |

两个游戏各自独立跑模拟，只是在互相汇报状态。**它们必然分岔**——
失步检测报的是**真话**，不是误报。

**这解释了为什么 frame 30 就分岔**：那不是「锁步有 bug」，而是**根本没有锁步**。

**修法方向**：在输入 hook 处，用权威输入流覆盖本地输入。
host 在 delay D 处对 frame N 有权威；guest 必须**应用** host 的输入字，而不是只把它画成幽灵。
th08-multi 和 th06_multi_net 都是这么做的——**输入流本身就是模拟**。

**为什么之前没发现**：因为失步检测之前根本不工作（见 §1.8 五个静默失败）。
检测器坏着的时候，看不见「对端输入没人消费」这件事——它只表现为「不同步」，
而「不同步」有无数种可能。**先修好观测手段，才暴露出真正的问题。**

## 2. 自动播放陷阱（今晚最大的坑）

**th08 无人操作约 26 秒后自动播放一个关卡**，`curState` 从 1（标题）变 2（GameManager），帧开始跑。

**这意味着**：
- 看到 `curState=2` + 帧前进，**不能**断言「有人在玩」。
- 之前我们拿自动播放的 300 帧当「锁步已证明」的证据，owner 戳穿后撤回。
- th08-multi 也有同样问题，他们的解法是**直接禁用标题 demo 播放**。

**我们已修**：DemoGate 车道加了 `human_latch`——读 `g_CurFrameInput` 判别。无人操作时 P2 不建、幽灵不发，日志打 `human=0 (ATTRACT/NO-INPUT)`。实测 PASS（1320 帧全程 0x0000）。

**判据**：`scene: frame=N curState=2 input=0x0000 last=0x0000 human=0` = 自动播放；`human=1` = 真人。

## 3. 反编译研究方法（三个项目共识，我们照做）

### 3.1 证据分级（不可推翻）

```
目标二进制字节 > 反汇编 > reccmp 匹配输出 > 继承的重建源码 > 邻近版本源码
```

低阶证据只能形成假设，**永远不能推翻目标字节**。观察和推断分开记。

### 3.2 有界重建循环

1. 验目标哈希 → 挑**一个**函数/地址段
2. 查 `mapping.csv` 定位
3. 看反汇编、调用者、被调用者、字符串、全局
4. 调和函数边界（一个 prologue + 一个 return）
5. 实现**最小**连贯改动，保持 VC7 x86 ABI
6. 构建**最小**目标，跑精确比对器（reccmp/objdiff）
7. 只更新到报告证实的程度
8. `git diff --check`，交接命令/结果/不确定

## 4. 协议地基（已定稿）

**THP 协议 v1**：
- 规范：`D:/Project/TH-Platform/docs/protocol/THP-PROTOCOL-v1.md`
- C11 参考实现：`D:/Project/TH08-Platform/protocol/thp_wire.h` 等 7 文件
- **80 个 `THP_STATIC_ASSERT`**，MSVC x86 `/W4` 编译通过
- 逐包适配表：`ADAPTERS.md`（TH06 18 行、TH08 17 行，每行带 file:line）

**核心设计**：
- 字节序做成结构体本身（`uint8_t b[N]` 存网络序），`sizeof` 精确、无需 `pragma pack`
- float 用**裸 IEEE-754 位** hash，不量化（x87/FMA 会让同源码不同位，量化会把真 bug 藏在绿 hash 后）
- 延迟非零时**必须延迟比对 hash**，否则静默关掉失步检测
- `VERSION_MISMATCH` / `BUILD_MISMATCH` 分开（th08-multi 混成一个）

**重要发现**：
- **TH06 失步检测 = 比 u16 RNG 种子**（`Controller.cpp:771`），不是 state hash，16 位很弱 + 15 帧盲区
- **TH08 失步 = FNV-1a 46 个 u32**，但只盖**弹幕/敌人计数**不含内容；失步直接杀进程**无 resync**
- **TH06 能自动修复失步**（主机权威重切+重置 RNG+恢复）
- → **THP 取 TH08 的 hash 检测 + TH06 的修复，两者都要**

## 6. 这个项目的血泪教训（每条都踩过）

1. **假死锁**：Go API stdout 管道不排空，~16 请求后 handler 阻塞在 `logger.Info`，进程活着像死锁。→ 永远 `ReadToEndAsync()`。
2. **假 404**：PS7 `Invoke-WebRequest` 读 4xx 状态枚举 `.value__` 返回 `$null`，所有真 404 看起来像失败，且不消费 body 导致下次请求卡死。→ 用 `HttpClient`。
3. **永远返回 0 的检查**：`Select-String -Path '…\**\*.go'` 不是递归的，永远报 `matches: 0`。我差点相信「CORS 没实现」。→ 用 `Get-ChildItem -Recurse`。
4. **空命令**：`pnpm typecheck` 因 solution-style tsconfig 恒退出 0。→ 真检查是 `tsc -b`。
5. **静默 skip**：Postgres parity 套件在 `THP_TEST_POSTGRES` 未设时**静默跳过**，我引用的「`go test ./...` exit 0」根本没跑数据库路径。→ 引用证据前确认它真的执行了。
6. **仪器坏了报成结论**：我的 SendInput 探针 C# 没编译成功，打印「NO INPUT REACHED THE GAME」——实际是仪器坏，不是方法不行。→ 脚本必须能区分「测到失败」和「没测到」。
7. **撤回的同步证明**：拿自动播放当人对局。→ 日志必须带 `human=` 判别。
8. **猜字节偏移**：窗口化先猜 offset 17，落在 `padYAxis` 里静默无效，几次全屏。→ 六个字段交叉验证才定下来 offset 34。
9. **写进 brief 的假事实**：我让 TH07 车道去查 `src/Global.cpp`，那文件从来不存在。车道靠实测推翻而不是照做——**这正是我们要的车道行为**。
10. **`%TEMP%\thp` 被清空了三次**。一次是车道清理时顺手删掉，另外两次原因不明。每次都要重建 `dll_build.ps1`、`dll_test.ps1`、输入器和全部冒烟脚本——这些是**共享**文件，TEMP 按定义没有作用域保护。→ **已根治**：构建/测试/输入器全部入仓到 `tools/th-debug/`，不再依赖 TEMP 存活。车道若发现 TEMP 被清空，用仓库副本，不要重建。
11. **绿灯的第三次伪装形态**：264 项单元测试全绿，而 5 个真实 bug 就住在里面——因为测试直接调 session API，**从不打开 socket**。→ `dll_test.ps1` 现在跑完会主动打印「本次绿灯不能证明什么」。**让工具自己说这些话，比写在文档里有用。**

### 7.1 构建指纹目前是零——诚实但无用（评审发现）

`thp_session.cpp:183` 现在把 `build_fingerprint` **全部填零**，注释写着：

> Claiming a fingerprint we did not compute would be worse than admitting we have none.

**这个态度是对的**，比虚报强。但后果是 `BUILD_MISMATCH` 永远不会触发，
而评审指出一个更要紧的点：

> 两台机器的 `th08.exe` 完全相同、但**我们注入的 netcode DLL 编译方式不同**
> （MSVC 版本、`/W4` vs `/O2`、x86 vs x64）会通过指纹检查，然后失步。
> **指纹必须覆盖 netcode 模块本身**，因为它才是两台机器之间最可能不同的部件。

**下一步**：对**我们自己的 DLL**（不是 `th08.exe`）算一个指纹填进去。

### 7.3 修复的七个静默失败 bug

全部靠「先让失败可见」定位，没有一个是读代码猜的：

1. 传缓冲区**容量**而非实际包长（发 76 收 512）
2. `reader_for()` 解码头部却丢进局部变量 → `ver_major` 恒为 0
3. NEGOTIATE + WELCOME 塞进一个 datagram → 接收端只解一个，WELCOME 静默丢弃
4. `on_hello` 五条拒绝路径全部不打日志
5. guest 的 `on_welcome` 从不回发 START → `type=4` 从未出现
6. `Action::Rejected/Starved/Disconnected` **零消费者**（写了没人读）
7. `store_local_hash` 的 `Result` 被丢弃 + 延迟分支不设 `desync_frame`
   ⇒ **失步检测器的假阴性**，而 `delay=3` 让延迟分支成为正常路径

### 7.4 一个我自己造成的教训

为了定位「哪些包类型真的到了」，我给收包路径加了**每包一行**日志。
